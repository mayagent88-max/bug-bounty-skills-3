# Verified Airdrop Research

## Check the full gate before you recommend

- Check the project's official hub, docs or announcement live with `browser.browse` and read the full eligibility path before you recommend it.

- List every gate in order, such as a score threshold, a connected account, a wallet registration, a snapshot or a deadline, and say which gate the user has not cleared yet.

- Treat a task list as incomplete until you have checked what follows the first action, such as post-claim tasks, and name any step you could not verify instead of guessing it.

- Check the current status live on the official source and give the date or deadline you found there, not a date from an older summary.

## Check what the user already did

- Check memory for whether the user already joined, registered or farmed the project before you say anything about their participation.

- Never state that the user did or did not join a project unless memory or the user confirms it, and ask for the wallet or account they used when that detail decides eligibility.

- When the user corrects a claim about their participation, save the correction in memory and use it in the next check of the same project.

## Verify the domain and the cost

- Use only the domain the official source names and warn the user when a circulating link uses a different domain.

- Separate free steps from paid steps and name the price or the paid multiplier before you mention it, and never present a paid step as required when the project offers a free path.

- Say plainly when a token has no confirmed date, no confirmed conversion rate or no confirmed reward, and do not promise a large profit from an unconfirmed allocation.

## Report per project and correct fast

- Report each project on its own with its link, its status, its next deadline and its open gates, so one project's update never hides another's.

- When a later check finds a gate or task you missed, correct the earlier report in the next reply and name what changed.

- Offer one next step at a time and ask whether the user wants ongoing monitoring before you set up a watch.

## Available connectors

- Use `muse.connector_search` to find other connectors and `muse.skill_search` to find related skills.

- If nothing here fits, look on the web for a maintained API or MCP server and set it up with [Custom Connectors and MCPs](/opt/muse/skills/custom-connector-setup/SKILL.md), or build a custom connector.

## Alternatives for better results

- When the official source is silent on a gate, check the project's announcement channel and say the gate is unconfirmed rather than skipping it.

- When a project needs a risky permission such as a browser extension that reads browsing, recommend an isolated profile and say what the extension can see.

- When the user is tired of a project or says to leave it, stop reminding them about it and keep only its deadline in the next plan if it still matters.
